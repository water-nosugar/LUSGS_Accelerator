# LU／RHS 等待区间分析与下一轮方案（2026-10-29）

建议围绕 **LU 因子更早发布、Lbar 输入单独就绪、Lbar 修正更早完成** 推进。1024 优先试验有界的下一列 LU 乘积提前计算；4096 同时需要重点处理 Lbar 输入的整体屏障。继续扩大因子缓存、增加 RHS 上下文或单纯提高 b 优先级，都不应作为首选。

本文重新读取第六轮已经完整验收的三组 8 槽轨迹，没有修改模拟器实现或执行新的优化仿真。新方案的收益均待实测，下面的周期拆分是现状测量。199 个已冻结实现文件逐一通过 SHA256 核对。

## 1. 等待究竟发生在哪里

关键 b 的每次逻辑发射与真实 RF 发射、宽度、owner 和返回一一匹配。三例共匹配 417792 个 b／LU 实际操作，并核对 2075862 次 LU／全部 RHS 逻辑与物理发射。拆分结果精确复现第六轮的 b 总区间。

| 当前 8 槽方案／单点平均周期 | 训练 1024 | 独立 s307 1024 | 验证 4096 |
| --- | ---: | ---: | ---: |
| 等 LU 列／主元发布 | 47.672852 | 46.582031 | 32.170654 |
| 发布后仍需等待倒数实际返回 | 54.705078 | 54.661133 | 13.170898 |
| 满足依赖后到发射 | 1.087891 | 1.041992 | 0.850830 |
| 算术固定延迟 | 95.000000 | 95.000000 | 95.000000 |
| 返回／局部发布 | 9.677734 | 9.626953 | 9.641846 |
| **b 总区间** | **208.143555** | **206.912109** | **150.834229** |

“等 LU 列／主元发布”包含该列算术推进和除法请求接纳，不能解释成纯 MUL／SUB 等待。当前代码在倒数请求被接受之后才发出 `LU_STEP_READY`。第二项只统计前一 b 操作已经返回、列已经发布之后，剩余的倒数返回等待，两项没有重复计算。

所有三个输入的 30720 次倒数运算，接受到真实返回均为 **12 周期**。训练 1024 中，各列最后一次 lower SUB 返回到倒数被接受，平均仅 0.51–0.73 周期；4096 为 1.46–1.60 周期，含未启用控制折叠的开销。因此主要问题是串行依赖和 12 周期服务延迟，增加 DIV 数量或减小启动间隔只能处理较小的接纳等待。

训练 1024 的因子等待进一步按列分布如下，列号从 0 开始：

| LU 列 | 等列／主元发布 | 等剩余倒数返回 | 合计／周期 |
| --- | ---: | ---: | ---: |
| 0 | 0.000 | 8.998 | 8.998 |
| 1 | 3.608 | 10.323 | 13.932 |
| 2 | 9.324 | 11.407 | 20.731 |
| 3 | 14.466 | 11.977 | 26.442 |
| 4 | 20.274 | 12.000 | 32.274 |

最后两列贡献训练输入因子等待的 **57.35%**；在 4096 中贡献 **84.06%**。应当重点让后面几列的 lower 更新和最终主元更早完成。

当前训练 LU 核心平均 148.66 周期，包含最后倒数实际返回则为 159.66 周期。最后 11 周期没有因为 `LU_COMPLETE` 已经发出而消失；优化必须同时检查 `LU_RECIP_READY`。

## 2. 前向最后实际等待的是 Lbar 修正

直接前向关系为 `f_i = b_i - Lbar_i * f_(i-1)`。前向合并需同时等 b 和修正向量就绪。我额外核对了 `DIRECT_BASE_READY`、`LBAR_READY`、`HANDOFF_CONSUME`、修正完成和实际合并发射。

| 当前方案 | 修正比 b 更晚的非首点 | 修正晚于 b 的平均周期 | Lbar 完成晚于前点反馈的点数 | 两个合并输入均就绪后的发射等待 |
| --- | ---: | ---: | ---: | ---: |
| 训练 1024 | 1023／1023 | 92.140 | 825／1023，80.65% | 0 |
| 独立 1024 | 1023／1023 | 95.172 | 822／1023，80.35% | 0 |
| 验证 4096 | 4095／4095 | 66.381 | 3428／4095，83.71% | 0 |

这是冻结时序中的先后关系，不能推断单独改变某一模块后的整线提速；共享 FU、RF 和前点反馈都会随新调度变化。不过它明确说明：**不能把 b 区间减少直接当成前向收益。应优先改善共享 LU 因子和 Lbar 的供给。** b 仍应得到必要的发射保障，但不宜为 b 的提前完成长期挤占 Lbar。

Lbar 与前点反馈都已就绪之后，到修正完成还需平均 22.25–22.78 周期。当前冷轮保留五次有序向量累加及其真实返回，这一段也不能通过提前设置 ready 标志消除。

整块输入完成时，训练／独立 1024 只有 136／154 个点的全部 LU 因子已就绪，4096 为 1967 个点。这是阶段边界比较：1024 更需要推进 LU；4096 约一半点的 LU 已被输入等待掩盖，更需要改善输入与 Lbar 求解的重叠。它不是额外可相加的等待项。

## 3. 方案 A：有界提前计算下一列的首个 LU 乘积

当前 Crout lower 更新为 `ell[r,c] = D[r,c] - ell[r,0]*u[0,c] - ...`，每项仍按原 k 顺序减去。已有双产品槽只允许同一阶段的下一个 k 乘法提前，不能跨当前列推进到下一列。

当第 0 列发布之后，后续列的首个乘积 `ell[r,0]*u[0,c+1]` 所需操作数已经稳定。处理当前列 c 的上三角点积、等待倒数或归一化返回时，可以利用剩余资源先算它。对 5×5 块，最直接的目标是列 2、3、4；列 1 的首个乘积仍依赖刚完成的第 0 行归一化，提前空间较小。

实施步骤：

1. 每个 LU 上下文增加至多一个未来列产品槽，绑定 token、generation、目标列和状态。
2. 只在操作数已真实发布、当前关键运算已获得发射机会后尝试；占用现有 MUL、RF 读取、局部标签和真实局部写端口。
3. 保留 MUL3 和一拍局部发布；下一列开始时仅消费已发布的 k=0 产品，随后继续原顺序 SUB。预计算尚未发出时走正常路径；已经发出但尚未返回时保留其所有权并等待真实返回，不能重复计算同一项。
4. 取消请求后仍排空真实在途操作；上下文不能提前复用。成功请求的 MUL／SUB 数量及逐位输出应与原方案一致。

在不受竞争影响且提前计算恰好被隐藏时，三个目标列各可能隐藏首个 MUL3＋发布1 的约 4 周期等待，约 **12 周期／块的局部调度空间**。这是理想估算，不是已测收益，更不能乘以点数当整线节省。

先按 `128 B × 4 个 LU 上下文 + 128 B 控制 = 640 B` 的保守预留设计，并完整核对 bank、标签与对齐。当前 1024 的 8 槽配置只余 320 B，因此第一版应使用 2 槽因子配置腾出容量；必须同时战胜当前 8 槽正式方案才有采用价值。4096 的 8 槽配置余 1216 B，有容纳该独立试验的空间。640 B 是设计预算，尚未实现或通过存储审计。

实现位置：[LU 产品发射](/home/zyy/gem5/src/arch/arm/cfd_coeff_preprocess_lu_rows.inc:5)、[有界产品窗口](/home/zyy/gem5/src/arch/arm/cfd_lu_products.hh:9)。4096 应保持原有单产品路径的其余条件，避免把开启双产品窗口的效果混进此消融。

## 4. 方案 B：Lbar 输入独立发布，解除 U／L 整体屏障

当前已有 D 的独立到达／SPM 读取，所以 LU 可以先启动；但是剩余 U／L 等输入仍合并在一个 `inputRead` 中，完成后才设置 `inputOperandsReady`。冷轮 Lbar、Ubar 的初始化又共用这个标志。因此 L 已可用时，Lbar 仍可能被其他输入、整体 bank 读取或 R 的启动门槛挡住。

建议分两次消融推进：

1. **先细分就绪条件。** 增加按块完成计数和真实 `L load done`、`U load done`、`R load done`；每个非重叠区间只读一次。Lbar 仅需 L 到达及其所需 LU 因子，Ubar 仅需 U 到达及其 LU 因子。保留现有有限 Onchip 队列、4 个 SPM bank 和 DMA 信用。
2. **再调整供给顺序。** 在已具备部分发布后，试验 D→L→U，R 使用单独受限供给；对未开启早 R 的 4096，必须让 R 有独立到达／读取条件，或允许已就绪的 Lbar 先启动。仅重排 D／L／U 而保留“全部输入完成才启动”的条件，收益会被屏障吞掉。

这里有两个必须一起处理的控制点。第一，当前 `startSolveRequests` 在 direct 模式下会因 R 未就绪而阻止整个请求启动；不能只改 `initializeRhs` 就宣称 Lbar 已可提前。第二，原停放契约只允许 b 完成且系数 RHS 尚未初始化时释放求解上下文。新的部分输入路径需要重新界定停放／恢复条件，只在没有部分执行或在途 RHS 时释放执行资源，并保持输入落地槽直到全部 DMA／SPM 访问完成。

4096 不宜直接恢复上一轮未采用的 8 深度早 R 配方。先测试前沿需要的 R／L 小窗口，让 Ubar 以有限年龄提升继续推进，避免推迟 Ubar 导致请求不能退休、反过来堵塞输入。

元数据优先使用已预留的 Request／OnchipContext 空间，并由 `sizeof` 和独立存储核算证明；超出预留则按实际存活请求数计价，不只按 4 个 LU 上下文计价。不能新增未计入预算的矩阵副本或无限读任务。

实现位置：[输入顺序](/home/zyy/gem5/src/arch/arm/cfd_coeff_preprocess_controller.cc:2157)、[整体输入读取](/home/zyy/gem5/src/arch/arm/cfd_coeff_preprocess_controller.cc:3805)、[RHS 初始化](/home/zyy/gem5/src/arch/arm/cfd_coeff_preprocess_controller.cc:4357)、[启动与恢复](/home/zyy/gem5/src/arch/arm/cfd_coeff_preprocess_controller.cc:4418)、[现有停放契约](/home/zyy/gem5/src/arch/arm/cfd_coeff_preprocess_controller.cc:4603)。

## 5. 方案 C：并行推进同列 lower 更新与 upper 分子

上三角分子为 `s[c,j] = D[c,j] - ell[c,0]*u[0,j] - ...`。其中 k<c 的 ell、u 均来自先前已发布列；它并不依赖当前主元 ell[c,c]。只有最终 `u[c,j] = s[c,j] * reciprocal[c]` 需要主元倒数。

当前状态机先 lower，后 upper 分子，共用 `luTemps` 和产品窗口。可以增加独立的有限 upper 累加状态，在 lower 执行时提前推进 upper 分子，最终同时等分子和倒数实际返回再归一化。两条链各自保留原减法顺序，不需要 FMA 或重新结合。

但已有实现已经让 upper 分子与倒数生成重叠，新增并行只能消除未被这个窗口隐藏的尾部。实测三个中间列的“upper 分子最后 SUB 返回晚于倒数返回”总和如下：

| 当前配置 | 列 1 | 列 2 | 列 3 | 合计／周期每块 |
| --- | ---: | ---: | ---: | ---: |
| 训练 1024 | 1.369 | 2.819 | 6.330 | 10.519 |
| 独立 1024 | 1.318 | 3.050 | 6.289 | 10.657 |
| 验证 4096 | 1.332 | 7.902 | 15.659 | 24.893 |

这些是冻结时序的暴露区间，不是可保证消除的收益。该方案对保留原串行产品配方的 4096 更值得研究。它需要额外累加器、产品槽、读写端口和阶段状态，风险高于方案 A；应在 A／B 单独验证后再试，不先同时改写全部 LU 状态机。

实现位置：[lower 到 upper 状态转换](/home/zyy/gem5/src/arch/arm/cfd_coeff_preprocess_lu_rows.inc:160)、[已有倒数重叠和归一化门控](/home/zyy/gem5/src/arch/arm/cfd_coeff_preprocess_lu_rows.inc:202)。

## 6. 其余方向的优先级

| 方向 | 建议 | 依据／边界 |
| --- | --- | --- |
| 缩短倒数硬件延迟 | 单列硬件方案研究 | 1024 有约 54.7 周期剩余倒数等待；12→8 周期只有在真实可实现且保持数值契约时才成立，不能仅修改仿真参数计作优化 |
| 增加 DIV 数量／降低 II | 后置 | 当前服务均为 12 周期，训练主元末 SUB 返回到接纳只有约 0.5–0.7 周期；吞吐改善不等于单次延迟缩短 |
| 增加 RHS 上下文 | 后置，部分发布后重测 | 当前 1024 四上下文全满约 16%；输入停放不占执行上下文；不能用总 RHS 区间推断上下文不足 |
| 继续扩大因子缓存 | 后置 | 2→8 槽减少约 1.7%–2.1% RF 读，但整线收益只有 0.046%–0.411%；新增缓存也挤占 A／C 的预算 |
| 因子命中／共享归一化读取 | 小范围试验 | 只在已就绪 RHS 中复用，不等待凑批、不延迟当前需要的 Lbar 列，首次读取和有限端口仍计价 |
| 结果旁路／更多局部化 | 仅在真实端口与发布模型下试验 | b 的 9.68 周期返回中，8 周期来自固定的行产品发布；不可把它设成零；已有全局 RHS 返回额外等待较小 |
| b 更高优先级 | 保留必要保障，避免永久抢占 | b 发射等待约 1 周期且所有非首点都先于修正完成；当前已有前沿优先与 LU 有界前瞻 |
| 改 RHS 求和树、FMA | 独立数值／架构分支 | 改变浮点结合顺序；以前的树和局部化试验已有退化，不能当作本轮顺序保持方案直接叠加 |

固定当前 RHS 运算顺序、MUL3／SUB4 及一拍局部发布时，b 的依赖链下限为 `95 + 8 = 103` 周期，尚未计其他竞争。4096 已有点实际达到 103 周期，b 区间中位数为 110 周期。后续应缩短等待较长的点并改善 Lbar 供给，不能预期所有点再靠调度大幅降低算术时间。

## 7. 实施顺序、比较口径与验收

第一批做两个互相独立的原型：A（下一列首乘积提前，首先面向 1024）和 B（输入按块发布，首先面向 4096）。B 先测部分发布，再测输入顺序。分别通过后才测组合；C 放在第二批。保持各规模原先采用的控制折叠、乘积窗口、R 预取等配方，避免一次改变多个条件。

每个原型与同二进制 2 槽对照比较，同时与当前正式 8 槽方案比较。训练 1024 当前 127195 周期、两个独立 1024 当前各 127048 周期、4096 当前 638987 周期。因为 A 可能需要退回 2 槽腾出预算，仅胜过 2 槽并不够。

核心记录应包括每列 `pivot／DIV accept／DIV return`，每块 `DMA complete／SPM load complete`，每个 RHS 输入就绪、发射与返回，Lbar 各列完成、前点反馈、修正完成、前向末点、后向末点和总完成。分别报告单点依赖区间、上下文占用、整线阶段边界；重叠时间不能相加。

采用标准是训练与固定独立输入的前向末点和整线完成共同改善，且存储预算、RF／FU 端口、实际 publication、输出数值与恢复均通过现有完整验收。若只让 b 启动更晚、降低等待计数，或只让 LU_COMPLETE 标志提前而实际倒数没提前，应判为无效。

保留 1／17 单元边界、65／71／72 的完整缓存与 warm 路径、4096 长线和取消／重试检查。不能为了新增局部槽挤掉短线完整系数缓存，也不能因前处理变快而忽略后向／输出尾部退化。
