# 单线第四轮：正确性修复、接口流量与有限缓存（2026-10-19）

本轮沿用单条网格线、每次调用一次前向和一次后向、FP64 5×5 块的范围。修复依据为 [10月18日检查报告](CFD_DSA_SINGLE_LINE_REVIEW_20261018.md)。先前归档结果保留原样，修正后的统计另行输出，不能把旧报告中的累计 bank 利用率继续用于瓶颈判断。

## 修改内容

1. **失败不能发布可复用缓存。** `commitTileChild` 在写缓存前确认子请求成功；任何子请求失败或父任务取消都会使整线缓存失效，停止新任务准入并取消其余子任务。全驻留对照路径也统一检查 `valid`，并禁止失败后重新发布缓存或用后续取消状态覆盖首个错误。已发出的 DMA 和记录保留自身快照，待子任务、记录、计算和片上访问收尾后，在 timing 接口下通过 DMA 发布错误状态并等待响应，才释放父任务。描述符仍在读取时发生的取消，也保留到描述符读取结束后完成收尾。
2. **统计区分累计快照、任务完成和诊断覆盖。** bank 计数只取每个 bank 的最后快照；后向阶段只把算术活跃与算术空闲作为可相加的两类。tile 等待和输出等待单独列为可能重叠的观察量。整线汇总记录只证明完成数、错误数和摘要，不虚构被省略的逐点诊断计数；客体统计明确输出逐点记录覆盖数，详细资源利用率从完整算术 trace 计算。
3. **提前拒绝模型不支持的粒度。** 启用片上 FP64 端口模型时，输入、tile 回读、warm interface 的宽度必须为 8B 的整数倍。40B 可以使用；41B、7B 等配置在仿真开始前报出明确错误。64B 是一次 DMA 请求的上限，仍按缓存行、页边界拆包，不是把每行40B填充成64B。
4. **可选的 warm 整线记录。** `--coeff-record-policy=warm-summary` 在 direct 系数命中的轮次，把 N 条160B记录改为一条64B整线记录；冷启动继续输出逐点记录，inverse warm 沿用原来没有逐点记录的路径。64B内含标识、generation、总点数、完成数、错误数、摘要及首尾时间。前向请求全部退休后即可传输，与后向计算及结果写回重叠；全部必要数据、整线记录和最终状态的响应仍纳入完成栅栏。逐点计算记录仍通过 trace 核验，摘要源值与客体回读值必须一致。这是接口策略变化，不是算术优化。
5. **可选的 warm 写回 FIFO 取数。** `--coeff-warm-y-source=fifo` 使用现有有界写回项中的40B结果快照发送 inverse warm y，省去先读回 SPM 才能发包的重复访问。y 仍写入 SPM，DMA 等待该存储完成，FIFO 保留到响应返回；没有增加随线长增长的隐藏结果数组。
6. **有界的两矩阵系数缓存。** `--coeff-line-cache-policy=adaptive` 优先保留完整600N字节缓存；direct 模式下完整缓存放不下、400N字节仍放得下时，只保留 LU/Lbar，通过 DMA 读取已保存的 Ubar。容量账本和片上端口访问按实际两矩阵计算，回读 Ubar 的流量与延迟全部保留。缓存键还检查 Ubar 后备地址，避免把上一地址的数据当成有效后备。此策略缓和容量边界，尚未实现任意片段驻留；超出400N容量或 `cache-cells` 上限仍然重建，inverse 仍要求完整缓存。
7. **显式 DMA 入口吞吐。** 新增全局 `--coeff-dma-issue-packets` 和 `--coeff-dma-issue-bytes`，按控制器周期限制成功接收的包数和有效字节数。重试不重复扣额度。0保留旧的未显式限速模型；正式对照同时使用1包/64B每周期，另设未限速对照。该值是可检查的模型假设，还不是物理硬件标定。
8. **验收和溯源纳入 runner。** 逐场景记录 guest 与 gem5 二进制 SHA256，CFD 模型、配置、benchmark 和工具的源码内容指纹，以及解析后配置和 CFD 环境变量；运行期间相关源码或二进制变化会导致验收失败。tiled 正常场景自动执行数值、运算次数、资源通道、容量、bank/端口、DMA响应闭合及记录生命周期检查。异常场景单独验证真实失败和取消后的重试与资源回收。
9. **按证据调整输入准入容量。** warm direct 的输入槽在65点原配置中平均占用约99周期，只有两个槽。新增2/4槽、逐点/整线记录的独立交叉对照；保持192KiB总预算、bank/端口和5乘5加1除不变，额外16,640B输入状态从同一预算扣除。已测17/65点采用4槽逐点记录较快，116点采用4槽整线记录较快；原默认值仍保留2槽，避免在线长和系数复用条件变化时无条件增加缓冲。

## 验证设计

数值检查使用独立 y/Δq 参考数组，参考 LU/Ubar 也放入独立临时区，参考求解结束后释放，不能预写硬件系数输出。测量前把硬件输出写成 NaN，并在系数重建时污染 LU/Ubar 输出。除与参考解比较外，还直接检查原始 D/L/U/R 的前后向递推残差；加入随机和尺度变化输入。原有 cache-contract 在命中时改变 R，并覆盖版本、线长、模式和 dirty 变化。本轮还以新接口策略重跑该契约。

新增原生 C 回归实际调用同一个参考函数：在硬件 LU/Ubar 输出区放入哨兵值，检查正常求解与分解失败后都保持不变，同时核对独立递推残差。把归档的旧参考函数放回同一测试中，会因输出哨兵被改写而失败；修正后的函数通过。独立参考工作区属于客体软件验证内存，不计入加速器 SPM；软件参考对原始输入和 CPU 缓存的预热仍然存在。

真实异常测试先触发 LU 失败，再同版本恢复正常条件重试；另覆盖描述符读取期间取消、计算进行期间取消及随后重试。日志篡改测试只用于检查验收器是否能拒绝坏证据，不计作硬件恢复测试。

补查全驻留对照路径时，实际复现了绕过缓存有效位的遗漏：在更新 D 后取消重建，再以同版本重试，旧路径命中旧缓存，最大绝对误差约0.00985，独立递推残差约0.01482。修复后 direct/inverse 的三次成功重试均为未命中重建，首个 LU 错误状态6不会被取消状态9覆盖。失败复现与修复后的正常结果分别保存，不能只凭最初未改变 D 的数值 PASS 判定缓存状态正确。

每组性能 A/B 固定 guest、gem5 和源码指纹，保持共享5乘、5加、1除以及3/4/12周期时延、除法II4不变。比较脚本明确列出配对：第一组只改变缓存/记录/取数策略；输入调参组只改变输入槽数，并核对新增容量、相同算术工作量及输出位摘要。缓存策略改变可能改变重建次数，因此运算量按各自实际命中序列独立验收，不要求两种策略的运算次数人为相同。

配对表比较的是同一算法模式的修改前后。沿用的 direct/inverse 推荐配置在 bank 数和上下文数上不同，因此不能用两种推荐配置的周期直接得出“同一存储硬件下哪个算法更快”的结论。算法模式的严格资源对照仍以 C 阶段固定配置为准；有限 SPM 下的模式选择需要另做统一 bank/端口和状态预算的实验。

资源利用率按控制器活跃窗口计算，不包含客体参考求解和逐轮数值检查。乘加发射槽利用率、流水中有运算的周期比例、整轮软件计时是三个不同口径。依赖反馈链中仍有算术执行时，未发射乘法不能直接归类为可消除的空泡。

## 性能与验收结果

**容量策略的单变量结果：** direct、116点、连续两轮、系数版本不变，在192KiB预算下，`full` 缓存放不下，命中序列为 `[0,0]`；仅改为 `adaptive` 后为 `[0,1]`，整轮累计周期由71,292降至48,344，减少32.2%。Ubar回读仍计入流量与延迟。这是避免重复重建的收益，不是提高算术器吞吐。

**输入槽对照：** 两边均使用 adaptive 策略，同一行的系数驻留类型、算术操作数、总DMA有效字节不变。17/65点均为一次重建后复用六次；116点为两轮。

| 场景 | 2槽周期 | 4槽周期 | 周期减少 | SPM预算占用峰值：2槽→4槽 |
|---|---:|---:|---:|---:|
| 17点direct，逐点记录 | 20,692 | 20,126 | 2.7% | 137,688→154,328B |
| 65点direct，逐点记录 | 56,974 | 55,458 | 2.7% | 166,488→183,128B |
| 116点direct，整线记录 | 48,286 | 46,930 | 2.8% | 173,888→190,528B |

额外16,640B包含两个输入缓冲及对应片上访问元数据，并非免费扩容。17点的warm控制器窗口约由1,791降至1,684周期。该实验没有继续增加RHS乘积缓冲的依据：16项缓冲的峰值仍为11项，满缓冲停顿为0。

**记录聚合减少流量，未单独提高吞吐。** 17点、七轮direct单独改整线记录，DMA请求有效字节由50,896降至34,960B，减少31.3%；控制器窗口累计同为16,107周期，客体整轮软件计时由20,674变为20,834，增加约0.8%。所以它保留为带宽选择，短线/65点时延候选仍用逐点记录。初版汇总在后向全部写回后才发送，会新增约106周期串行尾延迟；最终实现已提前发送，在后向期间隐藏该传输。

**FIFO取数的收益主要在端口访问。** 17点inverse单独启用FIFO取数，累计SPM读词从10,675减至10,165，少510个8B字；DMA请求有效字节不变，整轮周期18,866与18,868基本相同。不能把删除冗余读解释为该场景已获得明显提速。

**利用率只小幅改善，反馈依赖仍在。** 17点输入槽调参后，控制器活跃窗口内乘法发射槽利用率从14.52%增至15.04%，加法从15.91%增至16.48%，除法按II折算的发射槽利用率从38.87%增至40.27%。与此同时，全窗口“没有任何算术操作在执行”的比例从18.43%变为19.60%；该指标不能单独用于排序，因为启动/完成开销与运算重叠方式都影响它。验收以整轮耗时、正确工作量和容量/响应闭合为准。后向有序累加的反馈链仍限制同一点的并行度。

最终通过集合共138个仿真场景：性能对照33、压力22、缓存契约补测2、真实异常恢复10、原C回归35、原D回归24、输入调参12。另通过19项单元测试、23组无效参数拒绝和22组日志篡改拒绝。日志篡改拒绝用于检验验收器，真实异常恢复另计。

最终通过集合中，逐轮y/Δq最大绝对误差为5.55×10⁻¹⁶，原始递推式的最大归一化残差为3.25×10⁻¹⁶。这些结果针对已测合成输入，不代替真实CFD或病态矩阵验证。

所有上述仿真使用同一最终gem5和guest二进制，模拟源码、配置脚本和benchmark源码保持一致，按场景切换参数。验收器后来统一了“验证中”状态入口，缓存契约两项另行重跑；完整工具指纹分别保留，差异仅涉及两个验收文件。原始失败/中断尝试没有被改为通过，最终通过集合由 `evidence.json` 明确列出。

不同表来自各自的配对实验，不应直接相加百分比或把不同场景的周期拼成一次运行。

## 使用与复核

`single-line-round4-recommended.json` 收集了9个已验证的候选配置，按冷轮、连续复用、容量边界分别选择；它们不是统一bank数的算法对照，也不是任意线长的自动最优配置。

```bash
export LINKFLAGS_EXTRA='-Wl,--no-keep-memory'
scons build/ARM/gem5.opt -j2
python3 projects/cfd_dsa/tools/run_suite.py projects/cfd_dsa/suites/history/single-line-round4-recommended.json --campaign YOUR_UNIQUE_CAMPAIGN
python3 results/cfd_dsa/analysis/single-line-round4-20261018/verify.py
```

链接选项仅用于降低宿主机链接内存占用。证据复核默认还检查当前源码和二进制；以后改动工程后，可用 `--archive-only` 只复核冻结的历史证据。

## 边界

这里的 cold 指系数缓存未命中，不表示 CPU/L2/DRAM 全冷。软件参考求解和初始化在测量前执行，会影响相干缓存初态；本轮 A/B 保持这一过程相同，不能把结论推广成真实应用的冷内存延迟。DMA 请求有效字节也不是 DRAM 总线流量。

算术时序、SPM 宏端口和 DMA 端点时延仍是模型假设；寄存器读写端口、返回网络、选择网络、仲裁组合时序尚未完成物理标定，SimpleMemory 也没有替代真实 DRAM 控制器。本轮不据此推导面积、功耗或真实芯片频率，不把减少诊断流量解释成单线递推依赖已经消除。

adaptive 当前按矩阵类型保留 LU/Lbar，没有把剩余空间继续用于部分 Ubar，也没有实现任意片段驻留。它缓和已测的容量突变，但超过两矩阵容量或点数上限后仍会退化为重建，不能称为已经消除所有缓存容量断点。下一步可在同一容量账本下研究部分 Ubar 驻留，并核对额外的索引、有效位和仲裁成本。
